# todoke design baseline

## Status and scope

This document records architectural requirements for a free, open-source, cross-platform, end-to-end secure file transfer app. The goal is any-to-any transfers between phones and PCs, with adoption ahead of revenue and the ambition to outperform existing solutions across usability, reliability, performance, and security.

The runtime crates have a desktop application integrated with macOS, Windows, and Linux, and Android and iOS apps; the transports are TCP on the local network and tunnels through untrusted relays, and sessions are enabled only in development builds. Implemented so far:

- **Identity:** `DeviceBinding` and `Revoke` wire codecs in `todoke-proto`, and in `todoke-crypto` device and person identities, binding and revocation issuance and verification, a key-store interface with an encrypted software backend, and a contact store.
- **Sessions (suite 0x0001, not production-enabled):** prelude, Hello (58 bytes, no ratchet generation: §16 O12, [ADR 0016](adr/0016-hello-generation.md)), `NoiseHandshake`, transport frame, `Identity`, ratchet, `KeyUpdate`, Ping/Pong, and Error codecs in `todoke-proto`; in `todoke-crypto::session` the hybrid `IKpsk2`/`KKpsk2`/`XXpsk3` handshakes (Snow's reviewed HFS+PSK state machine over libcrux primitives, see [ADR 0001](adr/0001-noise-crate.md)), mutual identity confirmation, the PSK ratchet transaction with a durable journal in the contact store, encrypted framing with byte- and time-based rekey, keepalive, and an async adapter over `futures-io` byte pipes. Every entry point requires an explicit "unaudited suite" acknowledgement, which can only be constructed in unit tests or with the non-default `unaudited-suite-0001` feature (CI fails if a shipped graph enables it): PROTOCOL §16 keeps production sessions disabled until O6 and O10 close.
- **QR pairing (suite 0x0001, not production-enabled):** in `todoke-crypto::pairing` the §3.1 `QrPayload` (fixed 1312-byte layout and exact `TODOKE:` + RFC 9285 Base45 text, with every decoder check), the displayer's in-memory offers with one attempt per offer and the §13 unauthenticated-attempt budget, and a pairing authority that verifies the peer's binding, pins the responder's three keys from the QR, journals the pairing and burns the offer in one durable write (a ledger in the contact store), and creates the contact at the ratchet commit.
- **Human-code pairing (gated by O2, not production-enabled):** the §3.2 `CodeOfferRequest`/`CodeOffer`/`CodeShareA`/`CodeShareB` codecs in `todoke-proto`; in `todoke-crypto` a uniformly random 10-digit code, the offer's attempt budget (5 failures, 2-second spacing, one attempt at a time), CPACE-RISTR255-SHA512 from the `pakery` crates (draft-irtf-cfrg-cpace-21 vectors pass; see [ADR 0002](adr/0002-cpace.md)), the exact §3.2 context and PSK formulas, and the `XXpsk3` handshake and contact creation through the same pairing authority. It requires an explicit acknowledgement that only unit tests and the non-default `unaudited-code-pairing` feature can construct; without that feature no CPace code is compiled.
- **Content layer (not reachable from a shipped path yet):** in `todoke-crypto::content` the §8 per-file key schedule (fresh 32-byte master, per-epoch HKDF keys and nonce prefixes, STREAM BE32 nonces with the final flag, the 123-byte AAD), AES-256-GCM (libcrux-aes, advertised only with hardware AES) and XChaCha20-Poly1305 (libcrux), 16384-byte segments as Bao 0.13.1 combined slices (the `bao` crate, see [ADR 0003](adr/0003-bao.md) and [ADR 0004](adr/0004-content-aead.md)) with strict receiver checks, sender-side source-mutation detection, a receiver segment tracker for resume, and the `FileKey` body codec. Sealing and opening require an accepted-file token that only the verified-Accept path in `todoke_crypto::consent` creates (below); otherwise only unit tests and the non-default `insecure-content-without-accept` feature (benchmarks, fuzzing) can, and CI fails if a shipped graph enables it. The segment tracker caps each file at 4096 verified ranges and reports a refusal (`can_record`) before the receiver stores a segment.
- **Consent (not reachable from a shipped path yet, because sessions are gated):** the §6/§7 layout codecs in `todoke_proto::transfer` (`Capabilities`, `ManifestStart`/`ManifestPart`, the canonical manifest with every §7.1 schema rule including NFC names, `Accept`, `Reject`, `ChunkRequest`/`Chunk`, `ResumeQuery`/`ResumeStatus`, `Cancel`/`CancelAck`, `Complete`, `DeliveryReceipt`); in `todoke_crypto::consent` the manifest hash, issuance and verification of the signed Accept and delivery receipt against the session they belong to, and the only shipped constructor of accepted-file tokens ([ADR 0005](adr/0005-consent-api.md)). The committed `manifest-hash.json` and `accept-signature.json` fixtures are reproduced at runtime.
- **Transfer engine (suite 0x0001 sessions only, so not production-enabled):** `todoke-transfer` holds a sans-IO engine per session: the Capabilities exchange, explicit sender and receiver state machines (§11), the consent gate every `FileKey` and `Chunk` passes (its admission rules model-checked by Kani harnesses in CI and exhaustively tested locally; the engine's routing through it covered by tests), pipelined chunk requests within the §7.4/§13 budgets (at most `min(own, peer)` outstanding, two active files, two incoming transfers), cancel from either side with acknowledgments and bounded tombstones, per-session bounds on incoming transfer IDs and in-flight manifest bytes, resume in a fresh session with fresh consent (retained segments revalidated under the new keys, each file keeping its original content suite), Complete and the signed receipt, the §13 timers, and an events API (progress, speed, ETA, transport label, failures as stable codes with messages). An async driver runs it over a `Session`. Storage is behind the `SendSource`/`ReceiveSink` traits; in-memory versions exist for tests. The protocol defines no compression or content deduplication, so neither exists.
- **Files (desktop filesystems; reachable only through the gated engine):** `todoke-fs` maps every manifest name onto a safe local name before consent (bidi and invisible characters, look-alike and double extensions, shell-processed Windows files, device and short names, case- and normalization-insensitive collisions, per-OS length limits), with the exact local names, renames, warnings, and rejections available for the receive sheet. `FsSink` keeps only verified content ciphertext and file masters sealed through the platform `Sealer` in a private per-transfer quarantine with journals, tombstones, a quota, and start-up clean-up, and publishes each file after its length and whole-file BLAKE3 check through link-refusing, exclusive, no-replace operations bound to the checked file (a file substituted under the temporary name is never published or acknowledged) (rustix on Unix, the standard library on Windows; [ADR 0006](adr/0006-filesystem.md)), never setting execute bits or opening anything. Verified content is checked against its claimed type for UI warnings. `FsSource` serves offered files held open since hashing and refuses changed ones. On Android the app moves published files from app-private storage into the folder the user chose through SAF (renameat2 publication from Android 11, the exclusive copy before it: apps get no hard links); on iOS received files land in the app's Documents/Received, which the Files app shows; the Mark of the Web and `com.apple.quarantine` are platform hooks still to implement.
- **LAN transport (suite 0x0001 sessions only, so not production-enabled):** `todoke-transport` has `futures-io` links with what is known about them, a LAN address policy (private and link-local addresses on unprivileged ports only, for connections and accepted sources), RFC 8305 style connection racing within §10's bounds (connections race, sessions never do), dual-stack TCP with `TCP_NODELAY` on tokio, and a session manager: one attempt and one session per device pair with §4's simultaneous-attempt rule, the §13 unauthenticated-attempt budget before a Hello is read, Hello locators resolved through the discovery table, and migration as a fresh session on a better link (the receiver then accepts the resumed transfer again, §7.5). Direct Wi-Fi links (PROTOCOL §10.1 to §10.3: TCP with the unchanged session on every direct link, no direct QUIC) are set up inside an authenticated session: the engine checks and sequences `LinkAbilities`, `LinkOffer`, and `LinkAnswer` (one offer, exactly the chosen kind and the strongest security the joiner can join); the core, given a `LinkPlatform` (`Core::start_with_links`) and its `direct_links` policy (by default only to move off a relay), hosts or joins only for a transfer this user started or accepted, offers per-offer CSPRNG credentials, and moves the session onto the link (the host listens on its link address only and accepts that contact once; the joiner connects from its link address); the receiver's fresh Accept repeats the consent its user gave before the move. Desktops join (Linux through NetworkManager in-memory connections, Windows through temporary profiles) and host nothing: their hosting modes forward traffic or hand out routes and DNS, which §10.2 forbids; macOS takes no part (its join saves the network), and AWDL comes with the iOS links (P20). The device-lab matrix is `docs/qa/radios.md`. todoke uses no Bluetooth and no USB. See [ADR 0014](adr/0014-local-links.md) and [ADR 0018](adr/0018-desktop-links.md). See [ADR 0007](adr/0007-transport-and-discovery.md).
- **Discovery (LAN):** `todoke-crypto::discovery` derives each available contact's §9 discovery tokens and Hello locators from its committed pair PSK into a table without key material. `todoke-discovery` advertises one paired record at a time over mDNS (`mdns-sd`, logging off), rotating over contacts in a random order for a random 2 to 4 seconds each under a per-epoch random instance label, with stranger mode only on explicit enable; it checks every answer against the exact §9 shape and the LAN policy, keeps only matches within fixed bounds, and expires them after 120 seconds. Matching 1,000 contacts takes tens of nanoseconds per record; tokens are tested for unlinkability and clock skew. Multi-device enrollment and contact sync are not built: PROTOCOL §2 and §16 O4 forbid them in v1. See [ADR 0013](adr/0013-private-discovery.md).
- **Core, daemon, and CLI (development-gated: the `unaudited-dev` feature):** `todoke-core` is the one API every interface uses: requests (status, contacts, transfers, QR and code pairing in both roles, send, accept, decline, cancel) and events, served by a core thread that owns the identity (created on first use and sealed in a private state directory), the quarantine, the LAN listener, discovery, and every session; offers are built once a session has negotiated its suite (§6), and unfinished ones resume in the next session with a fresh Accept. `todoke-daemon` serves it to this user only over a local socket (peer user ID checked) or, on Windows, a loopback port with a token; it runs no commands, and prints systemd, launchd, and Windows logon-task definitions. `todoke-cli` is the `todoke` command, with `--json` and shell completions, escaping every peer-chosen name before printing it. Two daemons pair by code, transfer, survive the receiver being killed, and resume in the acceptance test. See [ADR 0008](adr/0008-core-daemon-cli.md).
- **History, visibility, and routes (core):** finished transfers are kept in a history sealed under the storage key, for a retention the user sets (§7.7 leaves receipt retention to local policy; default 30 days, 0 keeps none), with names, counts, the manifest hash, and the signed receipt on both sides; contacts report whether their session runs on the LAN or through a relay; a hidden device withdraws its LAN advertisement and relay presence. `todoke history` and `todoke visibility` expose them in the CLI.
- **Desktop app (GPUI through gpui-kit 0.7.3):** `todoke-desktop` is a window over the core API only: Home (contacts by proximity, multi-select, a drop zone, clipboard sending), the receive sheet (verified sender, counts, sizes, kinds, Accept all / Choose / Decline after a short arming delay), Transfers (progress, speed, time left, route), Pairing (QR, code, entering a code, pasting QR text; no comparison step, as §3 has none), History, and Settings (visibility with stranger mode as a five-minute pairing code, receiving, connections, retention, contacts, theme). It attaches to a running daemon or hosts one, so the CLI reaches the same core. Colors, spacing, type, and motion are tokens in one module (both themes WCAG AA); every control has a key and a screen-reader label; UI tests drive every flow against a mock core, and screenshots of every screen in both themes are rendered off screen. The toolkit's dependency tree has its own cargo-deny policy (`deny-desktop.toml`). See [ADR 0010](adr/0010-desktop.md).
- **Desktop OS integration and packaging:** the storage key moves into the platform's store (the Keychain, wrapped by a Secure Enclave key in entitled builds; DPAPI, wrapped by the TPM where present; the Secret Service), with a sticky, verified, one-way migration from the key file (§16 O9 for the storage key). A second launch hands its request to the profile's running window over an authenticated local endpoint; every send from outside the window (file managers, Finder's Quick Action and Share extension, Explorer's command and Share target, the global shortcut, the tray) opens a "Send to…" picker where the user chooses recipients after an arming delay. A tray or menu-bar item keeps the core running with the window closed and notifies offers without file names; login items, file-manager items, and the shortcut need no admin rights (XDG portals inside Flatpak). Packaging covers a notarised app and Homebrew cask, a signed MSIX with winget and Scoop manifests, and Flatpak, AppImage, deb, rpm, AUR, and nix, each installed, upgraded, and removed in CI. See [ADR 0011](adr/0011-os-integration.md).
- **Bindings (BoltFFI):** `todoke-ffi` and its generated Swift package, Android AAR (with a Kotlin guard that closes shared objects only after their calls finish), and npm package; the app supplies a key store, a notifier, and (reserved, refused while §16 O7 holds) radio links. Two cores pair, offer, accept, and receive through the binding in Rust, Swift, and Kotlin tests, and release libraries are checked to start no core; the generated C entry points run under Miri, the glue and the binding under AddressSanitizer, and random command sequences are fuzzed. See [ADR 0012](adr/0012-bindings.md).
- **Android app (P16):** `apps/android` in Kotlin and Jetpack Compose (Material 3 Expressive, a beta) on the AAR, Android 7 and later, one APK per ABI under 10 MB: the desktop's screens, a share target with Direct Share (shortcut IDs keyed hashes, never fingerprints), a Quick Settings tile, a widget, a foreground service while files move, WorkManager resumes, QR scanning with CameraX and ZXing (no Play Services in either flavor), the storage key wrapped in the Android Keystore (StrongBox, else the TEE) behind BiometricPrompt, documents handed to the core open, and a Baseline Profile. Compose tests of every flow with accessibility checks, and two real cores in the app's sandbox, pass on AOSP images of Android 7, 10, 11, and 16. See [ADR 0015](adr/0015-android.md).
- **iOS app (P17):** `apps/ios` in SwiftUI (Liquid Glass on iOS 26, system materials before) on the Swift package, iOS 17 and later, iPhone: the desktop's screens, a share extension (files queued for the app), share-sheet suggestions (keyed IDs), a visibility widget and Control Center control, a Live Activity with the Dynamic Island, Shortcuts and Action-button actions, VisionKit scanning, transfers in the background only in a continued-processing task the user started (iOS 26), with the core's background mode (`Request::SetBackground`) closing its listener and advertising nothing there (§10.3). The storage key stays in Rust, in the Keychain behind the Secure Enclave and Face ID (`Core::with_presence`, `TodokeError::Locked`), and §9 discovery goes through the system's Bonjour (`dns_sd`, the label as host name) because raw multicast needs a restricted entitlement. See [ADR 0017](adr/0017-ios.md).
- **Relay (§10):** `todoke-proto::relay` encodes and strictly decodes the relay control records. `todoke-relay` is a stateless node: QUIC v1 / TLS 1.3 (X25519MLKEM768 preferred, no 0-RTT or resumption), address validation and per-source limits, rooms in §10's order and limits, and byte-ordered tunnels with at most 1 MiB buffered per direction; it logs and keeps nothing, has totals-only metrics, and ships as a distroless image. `todoke-transport::relay` meets the other holder of a rendezvous token through a relay authenticated by the platform or a pinned key, picked from a shared relay list by rendezvous hashing, and never hole-punches (§16 O7). The core meets contacts with waiting offers back to back and every contact at a presence window, waits at the relay with a shown QR offer, and uses §4's roles on tunnels. Malicious-relay tests flip, replay, and drop tunnel bytes; NAT namespaces and a 10000-rendezvous load test run in CI. See [ADR 0009](adr/0009-relay.md).

The repository also contains offline Rust tools and reference cryptographic development dependencies for deterministic protocol fixtures. Requirements here are not claims about implemented runtime behavior. [The normative v1 draft](../spec/PROTOCOL.md) specifies wire records and the hybrid HFS+PSK construction from independently reviewed Snow source. Production backend secret handling, application integration, and interoperability remain release gates.

Read both documents before changing behavior. If specification and implementation disagree, stop and report the disagreement.

## Ownership and presentation

Rust owns all protocol, cryptographic, and file logic. The public entry point is `todoke-core`. SwiftUI on iOS, Jetpack Compose on Android, and GPUI on desktop present state and submit user intent. The core decides whether an operation is authorized. UI confirmation alone cannot bypass the signed AcceH requirement.

Mobile and web bindings use BoltFFI 0.31.1, pinned ([ADR 0012](adr/0012-bindings.md)). `todoke-ffi` exposes the core to Swift, Kotlin, and TypeScript as opaque handles (`Core`, `ContactHandle`, `TransferHandle`, `QrOffer`, `CodeOffer`, `Events`), blocking commands (no Rust future crosses: BoltFFI 0.31.1's Swift cancellation can poll a freed one), bounded event subscriptions, typed errors, and escaped plain values. No identity key, pairing PSK, session state, or file byte crosses; the storage key crosses only to the app's `KeyStore` (the Android Keystore's way in), and a pairing offer's text or code only when the app asks for it. The core does not run in a browser yet (browser mode comes later).

## Crate responsibilities and trust boundaries

The table assigns responsibilities. Apart from the identity, session, pairing, content, consent, and discovery-state code in `todoke-proto` and `todoke-crypto`, the transfer engine in `todoke-transfer`, the file handling in `todoke-fs`, the LAN transport in `todoke-transport`, mDNS discovery in `todoke-discovery`, the core, daemon, and CLI in `todoke-core`, `todoke-daemon`, and `todoke-cli`, the relay in `todoke-relay` and `todoke-transport`, the desktop app in `todoke-desktop`, the OS integration in `todoke-sys-macos`, `todoke-sys-windows`, `todoke-sys-linux`, and `todoke-shell-windows`, and the bindings in `todoke-ffi`, every crate currently contains documentation only and does not provide the APIs described here. The `todoke-bench` crate in `bench/`, an isolated workspace like `fuzz/`, holds benchmarks only.

| Crate | Responsibility | Trust boundary |
| --- | --- | --- |
| `todoke-proto` | Protocol representations, bounded parsing, and encoding of specified wire messages. | All peer-controlled bytes and decoded fields remain untrusted until the appropriate authentication and validation succeeds. |
| `todoke-crypto` | Use approved libraries for authenticated sessions, per-file encryption, verification, and secret lifecycle. | Isolate secret material; transport or UI input cannot select an unauthenticated or weaker security mode. No custom primitives. |
| `todoke-transfer` | Transfer state, consent enforcement, progress, and verified chunk orchestration. | Reject file bytes before a valid signed AcceH; authentication and integrity do not substitute for consent. |
| `todoke-fs` | File access, destination handling, and persistence of authorized transfer data. | Peer names and metadata are not filesystem authority; the local filesystem can change or fail during operations. |
| `todoke-transport` | Common byte-pipe interfaces and orchestration of the LAN, Wi-Fi peer-to-peer links, AWDL, and the QUIC relay (no Bluetooth or USB). | Every transport is untrusted; connectivity provides neither authentication nor consent. |
| `todoke-discovery` | Discover candidate peers and routes. | Discovery records identify candidates, not authenticated identities or authorized recipients. |
| `todoke-core` | Public facade joining Rust protocol, crypto, transfer, file, and discovery logic. | Validate caller intent and enforce policy independently of every UI, binding, and service caller. |
| `todoke-ffi` | BoltFFI boundary for mobile and web clients. | Foreign callers and foreign memory are untrusted; validate inputs and expose no secrets across the boundary. |
| `todoke-cli` | Command-line presentation and conversion of user intent into core calls. | Arguments, terminal input, and local callers do not bypass core policy. |
| `todoke-daemon` | Background lifecycle and service integration using the core. | Process/service requests do not confer peer authentication, file access, or transfer consent. |
| `todoke-relay` | Relay service for forwarding opaque encrypted traffic. | Treat connected clients as hostile and the relay itself as untrusted by endpoints; it receives no endpoint secrets. |
| `todoke-preview` | Bounded, isolated handling of previews derived from authorized content. | Received content and metadata can be malicious even when sent by an authenticated peer; preview paths cannot bypass consent. |
| `todoke-desktop` | Thin GPUI desktop presentation over the core (gpui-kit). | UI state and callbacks express intent; the core remains the authority for protocol, consent, and file operations. Peer-chosen names are escaped before display. |
| `todoke-sys-macos`, `todoke-sys-windows`, `todoke-sys-linux` | OS bindings: platform key stores; with the `desktop` feature, login items, file-manager items, portals, Services, the Share target. | No protocol, consent, or file logic; unsafe code only in reviewed modules, each block justified. |
| `todoke-shell-windows` | The Explorer command (an `IExplorerCommand` COM server) of the MSIX. | Hands selected paths to the app; decides nothing and reads no file. |
| `todoke-sys-windows` | Narrow Windows operating-system integration. | OS API results, handles, and callbacks must be validated; keep any necessary unsafe code inside this boundary. |
| `todoke-sys-macos` | Narrow macOS operating-system integration. | OS API results, handles, and callbacks must be validated; keep any necessary unsafe code inside this boundary. |
| `todoke-sys-linux` | Narrow Linux operating-system integration. | OS API results, descriptors, and callbacks must be validated; keep any necessary unsafe code inside this boundary. |

This is an ownership map, not a dependency graph. Concrete APIs, dependency edges, service IPC, mobile OS adapters, and preview isolation must be designed with their associated implementation. In particular, `todoke-sys-macos` does not establish that an API is available on iOS.

## Security requirements

Every session must authenticate with Noise using IKpsk2, KKpsk2, or XXpsk3, hybrid X25519 + ML-KEM-768, and a pairing PSK ratcheted per session. The protocol draft assigns the exact HFS+PSK token schedules, message layouts, transcript requirements, and a conservative ratchet transaction. HFS uses a fresh ephemeral ML-KEM key, not the draft's retained static ML-KEM credential. The construction follows independently reviewed Snow source; the new ML-KEM backend and todoke integration are not covered by that audit. `todoke-crypto::session` implements it and reproduces the committed handshake transcripts byte for byte. Suite 0x0001 remains disabled for production pending the secret-lifecycle (O6: Snow and libcrux leave some secret temporaries unwiped, listed in ADR 0001) and interoperability (O10) gates.

Per-file content must use AES-256-GCM STREAM encryption, with XChaCha20-Poly1305 as the fallback, and BLAKE3/bao verified chunks. The protocol draft specifies STREAM BE32 substreams, nonce allocation, authenticated suite selection, encrypted Bao slices, and chunk framing. Authenticate and validate according to that specification before treating data as trusted; standalone nonce vectors are not complete content-encryption conformance evidence. `todoke-crypto::content` implements the cryptographic part and reproduces the committed nonce and key-schedule fixtures, Wycheproof, and Bao 0.13.1 reference slices; a device advertises AES only where libcrux uses hardware AES (ADR 0004), so phones currently use XChaCha.

Consent is enforced in the core: no file byte is accepted before a signed AcceH. The protocol now defines AcceH as the session-bound, Ed25519-signed Accept record and specifies its authority, canonical bytes, selection, expiry, and replay rules. No pre-consent preview or alternate transport may evade it. `todoke_crypto::consent` issues and verifies that record against the session and manifest and is the only shipped source of the token the content layer needs; `todoke-transfer` passes every incoming key and chunk through a consent gate first ([ADR 0005](adr/0005-consent-api.md)).

Use libcrux wherever it covers the requirements, otherwise appropriate RustCrypto/dalek crates. Never implement cryptographic primitives. Zeroize all secrets, never log them, and never pass them across FFI, with one exception: the 32-byte storage key crosses to and from the app's `KeyStore` on mobile, the only way into the Android Keystore ([ADR 0012](adr/0012-bindings.md) records the residual risk). Do not collect telemetry. These requirements also apply to diagnostics, errors, examples, tests, and future platform integrations.

All crates outside `todoke-ffi`, `todoke-sys-*`, and `todoke-shell-windows` forbid unsafe code. Those deny it except in reviewed modules; `todoke-ffi`'s only unsafe code is what BoltFFI generates. Any future exception must be narrow, reviewed, and documented. Untrusted inputs must produce recoverable errors rather than panics. The protocol assigns wire budgets and failure rules; platform resource management and crash behavior still need implementation evidence before network-facing features are added.

An encrypted authenticated session does not make peer-supplied paths, content, or resource requests safe. The protocol and file boundaries must account for malicious authenticated peers as well as hostile transports. This baseline makes no anonymity or traffic-analysis-resistance claim.

## Verification and change discipline

Every parser receives a cargo-fuzz target; every state machine receives proptest state-machine tests. Add meaningful tests alongside the implementation and keep documentation in the same pull request. Formal models belong in `formal/`, and reproducible performance measurements belong in `bench/`.

The scaffold's build and policy checks establish repository hygiene only. Cross-target checks of empty libraries do not establish that native APIs, BoltFFI, transports, or applications work on those targets. Native OS checks, mobile/web integration checks, adversarial testing, and security review must grow with functionality.

## Decisions required before implementation

The authoritative list is in [spec/PROTOCOL.md](../spec/PROTOCOL.md#open-decisions). Architecture additionally needs explicit choices for preview isolation, platform permission handling, daemon IPC authorization, platform secret storage, and dependency/API boundaries.

The device's X25519 Noise static key has a zeroizing type but no key-store custody yet; callers hold it until a key-store role for it exists. Secret storage has a core interface but no platform backend. `todoke-crypto` keeps signing keys behind a `KeyStore` trait. Its encrypted backend persists one sealed blob through two hooks: a `Sealer` (authenticated encryption under a key the backend protects) and a `BlobStorage` (atomic whole-blob replacement). The software backend seals with ChaCha20-Poly1305 under a caller-supplied key. The storage key that seals this state now lives in the platform's store on the desktop (the Keychain with a Secure Enclave wrapping key, DPAPI with a TPM wrapping key, or the Secret Service; ADR 0011), falling back to a private key file only where no store exists (a server without a session bus) or when configured. On iOS it lives in the Keychain behind the Secure Enclave (ADR 0017) and on Android in the app's Keystore-backed store (ADR 0015); keeping the signing keys themselves in hardware remains open (O9). Rollback resistance of stored state remains a gate (O3). The protocol draft resolves wire choices where stated and explicitly gates unresolved construction, platform, and secret-lifecycle questions.
