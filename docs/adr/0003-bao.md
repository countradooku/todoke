# ADR 0003: Bao library for verified segments

- **Status:** proposed (needs maintainer approval). The library is used by
  the content layer in `todoke_crypto::content`, which is not reachable from
  any shipped path yet: sealing and opening need a verified Accept, which
  the transfer layer has not built.
- **Date:** 2026-10-13
- **Scope:** the implementation of the Bao 0.13.1 combined slice encoding
  for content segments. The format itself is fixed by
  [PROTOCOL §7.4](../../spec/PROTOCOL.md): an 8-byte little-endian length,
  then the canonical pre-order stream of 64-byte parent nodes and BLAKE3
  leaves of up to 1024 bytes, at most 32768 bytes per slice; the empty
  encoding is eight zero bytes. This ADR only selects the library and
  records the checks todoke adds on top of it.

## Context

PROTOCOL §7.4 pins the
[Bao 0.13.1 specification](https://github.com/oconnor663/bao/blob/0.13.1/docs/spec.md)
and forbids a bespoke Merkle format. PROTOCOL §14.2 requires "official
BLAKE3/Bao libraries" and forbids implementing primitives, so todoke must
not hand-roll tree hashing. The receiver rules are strict: authenticate the
AEAD first, then check the header and range, consume the whole canonical
slice with no trailing bytes, get exactly the requested byte count, verify
against the manifest root, and never accept a decoder's permissive
past-end-of-file or partial reads.

Requirements:

1. Byte-identical Bao 0.13.1 combined slices and roots, shown against
   reference outputs.
2. Slice extraction from a file plus an outboard tree (the sender must not
   keep a second full copy of each file).
3. A decoder that verifies every parent and chunk before releasing bytes.
4. No panic on hostile input (after todoke's own checks), no `unsafe`,
   permissive license, latest release, few dependencies.

## Decision

Use **`bao` 0.13.1** (`=0.13.1`, a direct dependency of `todoke-crypto`),
with these todoke additions in `content/slice.rs`:

- **Range first.** The requested range must lie inside the file and be at
  most one segment; length zero is legal only as the empty file's single
  segment. `bao`'s decoder otherwise verifies the final chunk and returns
  nothing for a slice past the end, or returns a short read for a slice
  crossing it.
- **Header equals the manifest size,** checked before decoding. Bao
  authenticates the length only through the final chunk, so for a slice
  that does not reach it, `bao`'s decoder accepts some wrong headers (a
  test demonstrates this). Checking first also keeps hostile lengths away
  from the decoder's internal assertions.
- **Exact byte count.** The output buffer is exactly the segment length and
  is filled with `read_exact`; the empty file runs the decoder's
  zero-length verification of the empty root chunk.
- **No trailing bytes.** After decoding, the decoder must have consumed the
  whole slice. Because the decoder's reads are fixed by the (now checked)
  length and range, and every byte it reads is verified, this makes the
  accepted slice exactly the canonical one.
- **Sender check.** The sender extracts each slice from the source file and
  its outboard with `SliceExtractor::new_outboard`, then runs the same
  verifier against the manifest root before sealing. A changed source or
  outboard is refused, so the same key and nonce never encrypt different
  plaintext (§8).

## Conformance evidence (all in `cargo test --workspace`)

- **Bao's own vectors.** `crates/todoke-crypto/testdata/bao/test_vectors.json`
  is the file from the Bao repository at tag 0.13.1 (provenance in that
  directory's README). `bao` reproduces every hash, combined encoding, and
  outboard encoding, and every slice from both the combined and the
  outboard form, byte for byte; its decoder rejects every listed corruption
  point. The strict verifier accepts each slice exactly when its range lies
  inside the file and returns the right bytes; it rejects the 40+ lenient
  cases (zero-length, crossing, or past-the-end ranges) that `bao` alone
  accepts.
- **todoke segment slices from an independent implementation.**
  `segment_slices.json` was generated by `generate_segment_slices.py` with
  the pure-Python reference implementation `tests/bao.py` from the same tag
  (its own BLAKE3, no shared code with the Rust crate): 14 file sizes
  around chunk and segment boundaries up to 34 segments, every segment's
  slice length and BLAKE3 hash, full bytes for small files. The sender's
  extraction matches all of them and the verifier returns each segment.
- **Hostile slices.** Every single-bit flip (all positions of small slices,
  sampled for large ones), wrong root, another segment's slice, truncation,
  trailing bytes (1, 64, 1024 bytes, or the next slice), wrong length
  headers, oversize slices, and the empty file's exact eight zero bytes
  (with 7, 9, or a nonzero header rejected).
- **Fuzzing.** `crypto_content_bao_slice` feeds arbitrary slices for every
  segment of files up to five and a half segments and asserts that any
  accepted slice yields exactly the right bytes.

## Consequences

- Throughput: `bao` hashes one 1024-byte chunk at a time, so it does not use
  BLAKE3's multi-chunk SIMD. On an Apple M5 Pro, building an outboard runs
  at about 1.1 GiB/s and a sealed or opened segment at 300–500 MiB/s
  (`bench/README.md`); Bao hashing, not the AEAD, dominates. Acceptable for
  v1; a faster implementation would need the same byte-identity evidence.
- `bao` 0.13.1 is 18 months old with no newer release; it is small and the
  format is frozen. Its cargo-vet entry is an exemption ("Not yet
  reviewed"); a real review is part of gate O6.
- Its decoder keeps a copy of the most recent chunk in an internal buffer
  that is not zeroized. Chunks are file content, not keys.
- An outboard tree is about 6.25% of the file size (64 bytes per 1 KiB
  chunk). Senders store it on disk next to the file (`write_outboard`);
  the in-memory `outboard` helper is for small files and tests.

## Alternatives rejected

- `bao-tree`: not the reference, compatible only under conditions that
  todoke would have to enforce, and a much larger dependency graph.
- Hand-written tree hashing: forbidden by the protocol.
