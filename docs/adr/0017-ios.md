# ADR 0017: The iOS app

- **Status:** accepted on 2026-10-16. The design was delegated with the
  standing priority of maximum security first, then performance. Where the
  P17 build prompt and PROTOCOL differ, PROTOCOL wins (below).
- **Date:** 2026-10-16
- **Scope:**
  - `apps/ios` (the app, its share and widget extensions, its tests) and
    `.github/workflows/ios.yml`
  - `todoke-sys-macos`: the Keychain on iOS with a presence requirement,
    and `bonjour` (`dns_sd`)
  - `todoke-discovery::Bonjour` and the core's use of it on iOS
  - `todoke-core`'s `ProfileError::StorageKeyRefused` and
    `Request::SetBackground`, and `todoke-ffi`'s `TodokeError::Locked`,
    `Core::with_presence`, and `Core::set_background`
  - `crates/todoke-ffi/boltffi.toml` (iOS 17) and `boltffi.ios.toml`

## Context

The P17 prompt asks for `apps/ios` in SwiftUI (Liquid Glass) on the
BoltFFI Swift package, the oldest iOS the required APIs allow (documented),
with:

- the desktop's screens (P12) and the settings mockup;
- a share extension, share-sheet contact suggestions through
  `INSendMessageIntent` donations, a Control Center control, a widget,
  Shortcuts actions, Action button support;
- a Live Activity and the Dynamic Island for transfers, background work
  with honest limits;
- QR scanning with VisionKit's `DataScannerViewController`;
- a key store: "Ed25519 key wrapped by a Secure Enclave P-256 key; Face ID
  gating via LocalAuthentication";
- Files app integration for the received folder;
- acceptance: XCUITest for every flow, a VoiceOver and Dynamic Type pass,
  an App Store privacy label of "no data collected".

## Decisions

### Platforms

| | |
| --- | --- |
| Minimum | **iOS 17.0**: the core experience needs Observation, App Intents in widgets (the Live Activity's Cancel button, the widget's toggle), Action-button shortcuts, and the accessibility audits the tests run. VisionKit's scanner (iOS 16) and Live Activities (16.1) fit below it. |
| Later only | The Control Center control (iOS 18), Liquid Glass surfaces and the continued-processing background task (iOS 26): behind availability checks, with system materials before (and, before iOS 26, no transfer in the background). |
| Devices | iPhone. |
| Toolchain | Xcode 27 (iOS 27 SDK), Swift 5 language mode, the Swift package BoltFFI packs for iOS 17 (device and simulator slices). |

Standard bars, tab bars, and sheets adopt Liquid Glass on their own on
iOS 26; todoke's floating action bar and buttons use `glassEffect` and the
glass button styles there. Content cards stay on solid surfaces: text on
glass lost contrast in the accessibility audit, and glass is for the
controls layer.

### Keys: the Keychain and the Secure Enclave, natively

The prompt's "Ed25519 key wrapped by a Secure Enclave P-256 key" is met
through the storage key: the core seals its Ed25519 identity (and all its
state) under the 32-byte storage key, and that key is stored in the
data-protection Keychain wrapped by a P-256 key in the Secure Enclave
(ECIES, X9.63 SHA-256, AES-GCM), "this device only", never synchronised or
backed up. Unlike Android, nothing crosses the boundary: `todoke-sys-macos`
does this in Rust on iOS as on macOS (`Core::new`), so the key never
exists in Swift memory.

**Face ID gating:** when the device has a passcode as the profile is
created, the app starts the core with `Core::with_presence` (which accepts
only the `Platform` key policy: any other could fall back to a file): the
Secure Enclave key carries a user-presence access control, so the system
asks for Face ID, Touch ID, or the passcode (LocalAuthentication) each
time the key is unwrapped, which is each time the core starts. The
decision is taken again whenever there is no profile (after a restore
from a backup, which never holds the state); Settings says which applies.
A cancelled or failed prompt (user, system, or app cancel, failed
authentication, not interactive; `errSecUserCanceled`,
`errSecInteractionNotAllowed`, and on iOS `errSecAuthFailed`) is
`PermissionDenied`, which the core keeps as
`ProfileError::StorageKeyRefused` and the binding reports as
`TodokeError::Locked` (the app shows Unlock). Biometry lockout, no
passcode, no enrolment, and every other error are `KeyStore`, with the
reason, as is a key that is gone or damaged. Android's refusing Keystore
maps to `Locked` too.

iOS has no weaker store to fall back to: never the login keychain (an
item not "this device only" could travel in backups), never a raw key on
a device when the Secure Enclave fails (every supported iPhone has one; a
raw key is kept only on macOS and the iOS Simulator, where the enclave
may be missing), and never the `Auto` policy, which could become a file.
A wrapping key left by a store that did not finish is replaced, never
reused with an access control it may not have.

### Discovery: Bonjour through `dns_sd`

An iOS app may not send or receive raw multicast without Apple's
restricted `com.apple.developer.networking.multicast` entitlement, so
`mdns-sd` cannot run there. Services declared in `NSBonjourServices`
(`_todoke._tcp`) go through the system's mDNSResponder instead, which the
local-network permission covers. `todoke-sys-macos::bonjour` binds
`dns_sd` (register, address records, browse, resolve, get-addr-info): one
thread owns every `DNSServiceRef` on one shared connection; the reviewed
unsafe code stays in that crate.

What is advertised matches §9 and the `mdns-sd` backend: one instance per
wanted record, its rotating label as the instance name **and as the host
name**, with its own address records (probed as unique), the service and
the records registered only on interfaces with a private or link-local
address (an address whose interface index is unknown is skipped).
`dns_sd` would otherwise name the device's own host (often derived from
its name), and that stable name would link every rotating label. Answers
pass `Sighting::check` and the LAN policy; the stranger record is
withdrawn after `STRANGER_MAX` whatever the caller asks. The core uses
Bonjour on iOS (`mdns-sd` is not built there) and `mdns-sd` elsewhere.

Everything stays on the LAN and on multicast, as with `mdns-sd`: browsing
and registering are in `local.` only (never the wide-area domains a
network may configure), only §9-shaped labels are resolved, a resolved
host outside `.local.` is dropped before any lookup (a unicast query for
a name a stranger chose would leave the network), and addresses are
looked up with `ForceMulticast`. At most 64 instances are resolved at
once; one that does not resolve within 30 seconds, or whose TXT is not
one `v1=` string, gives its slot back. If mDNSResponder's connection
breaks, the thread ends instead of spinning and the backend starts
another (at most every 5 seconds). Interfaces are read every 5 seconds,
and only changes reach mDNSResponder.

### Lifecycle and background, with honest limits

§10.3: on iOS a transfer runs "in the foreground or in a
continued-processing background task the user started", and the app
closes its TCP listeners in the background.

- The core starts when the app comes to the foreground (once; concurrent
  starts share it). With a gated key, each start asks for Face ID.
- When the user sends or accepts (in the foreground, as iOS requires), the
  app asks for a continued-processing task (iOS 26; it starts then or not
  at all). The system shows its progress and the user can stop it; it
  ends once nothing has moved for a few seconds.
- When the app leaves the foreground with that task running, the core
  enters its background mode (`Request::SetBackground`): the listener is
  closed, nothing is advertised (paired or stranger), relay presence ends
  (waits in progress are cancelled), pairing ends and is refused; open
  sessions and the reconnections that sends waiting for a contact need go
  on. Back in the foreground the listener reopens as at start, on a fresh
  port (never the old one again, which another program may have taken),
  and discovery restarts with it. When the task ends with the app in the
  background, the core stops.
- Otherwise the core stops when the app leaves the foreground, before
  iOS 26 too: a short background task is not what §10.3 allows. A stop
  while a start is under way wins: the core that start opens is released
  at once.
- No refresh task: one would have to start the core, which listens.
  Interrupted transfers resume when the user opens the app (§7.5).
- So nothing new is received while the app is in the background: offers
  wait for the app (they expire after 300 seconds, §13).

### System integration

- **Share extension:** it cannot run the core (an extension's memory
  budget, and the profile belongs to the app), so it moves the files into
  the App Group with the chosen contact and the app sends them when it
  next runs, and says so. All or nothing: if one attachment cannot be
  read, nothing is queued and the share fails. Queued files are protected
  while the device is locked unless open, and excluded from backups. Each
  queued request is sent once (one pass at a time, marked with its
  transfer) and its files are removed once that transfer ends; a request
  that fails is tried again, backing off, and dropped after five tries,
  the user told; a folder the extension never finished goes after a day.
- **Share-sheet suggestions:** each send donates an `INSendMessageIntent`
  whose conversation and recipient are the contact's keyed ID
  (HMAC-SHA-256 of the fingerprint under a random key of this install,
  128 bits), never the fingerprint; the share extension supports the
  intent and preselects the contact.
- **App Group contents:** the visibility setting, the contacts' names and
  keyed IDs, the share queue, and Live Activity cancel requests. The
  storage key stays in the app's own Keychain group, which the extensions
  cannot read.
- **Widget, Live Activity, Control Center:** the visibility widget and the
  Control Center control (iOS 18) change visibility through an App Intent;
  the Live Activity shows the total progress, the contact's name for a
  single transfer, never file names, and a Cancel button (a Live Activity
  intent the app's process runs).
- **Shortcuts and the Action button:** "Send files with todoke" (asks the
  user to confirm, so an automation cannot send unseen; then queues like
  the share extension and opens the app), "Toggle todoke visibility",
  "Pair a device with todoke" (opens the pairing screen, where the QR, and
  with it stranger advertising, waits for a tap). Any of them, or the
  Control Center control, can be the Action button's action.
- **Notifications:** an offer shows the sender's name and counts, never
  file names. Whether that shows on a locked screen is the user's setting
  (hidden by default on Face ID iPhones, shown on Touch ID ones).
- **Files app:** received files go to `Documents/Received`, which the
  Files app shows (`UIFileSharingEnabled`,
  `LSSupportsOpeningDocumentsInPlace`); the core's state lives in
  Application Support, excluded from backups.
- **Sending:** documents picked are opened in the app (inside their
  security scope, `O_NOFOLLOW`) and handed to the core open, as on
  Android.
- **Pairing screens:** iOS has no per-window secure flag; their content is
  hidden while the screen is recorded or mirrored and in the app
  switcher's snapshot.
- **Privacy manifest:** no data collected, no tracking; the required-reason
  APIs are the App Group's defaults, file timestamps, and disk space.

### QR scanning and O5

VisionKit's scanner reads QR codes only and passes on only text starting
with `TODOKE:`. As on Android, the scanned text (the QR's secret included)
is a Swift `String` before `pair_scan_qr` takes it (§16 O5, recorded, not
resolved). Showing a QR passes no text.

### Testing

- **The real core in the app's sandbox** (XCTest, the development
  package): two cores pair by QR, the scanner finding the displayer over
  Bonjour; a file handed over open is sent, accepted, and published; the
  key is in the Keychain behind the Secure Enclave (the simulator on Apple
  silicon has one); a profile reopens with its identity; a key needing
  presence never falls back to a file.
- **Every flow** (XCUITest against a scripted core that debug builds alone
  contain): home, accepting whole, choosing, declining, programs, resumed
  offers, pairing by QR and by code, pairing opened by a shortcut (no QR
  before a tap), scanning without a camera, cancelling a transfer,
  clearing history, hiding.
- **The background mode** (Rust, two cores): in it the listener's port
  refuses connections, nothing is advertised, pairing is refused, and a
  send in the open session still arrives; back, the listener is on the
  same port and the record returns.
- **Accessibility:** each screen goes through the system's accessibility
  audit (contrast, hit regions, labels, Dynamic Type, clipping), and every
  tab at the largest accessibility text size. The audit found and the app
  fixed: text on glass, faint secondary and tinted text, a red too light
  for normal text (now a darker adaptive red, semibold), disabled buttons,
  a progress bar as its own tiny element, rows and labels that clip at
  large sizes, toolbar and list buttons that did not scale. Four
  exceptions, each narrow and checked by hand:
  - elements partly beneath a system bar (read once scrolled into view);
  - contrast issues the audit ties to no element: in every case seen,
    content below the fold faded by the tab bar's scroll-edge effect
    (screenshots checked);
  - the Dynamic Type check alone for two whole-row buttons ("Open in
    Files", "Clear the history") that the audit misreads at the default
    size: a test measures them at the default and the largest size and
    requires them at least to double;
  - clipping of the system search field (`.searchable`), Apple's own
    control.
- **Bonjour** on macOS (no multicast needed): an instance round-trips; two
  contacts find each other and see the withdrawal; only §9 labels and
  `.local.` hosts are followed.
- CI (`ios.yml`) runs the unit and UI tests on a simulator, and builds a
  release app against the shipped package, checking it carries the privacy
  manifest and no test hook.

## Consequences

- A release build (sessions disabled, PROTOCOL §16) shows why it cannot
  transfer, as on the desktop and Android.
- The app receives only while it is open; files shared from other apps
  wait until it is opened.
- With Face ID gating, every foreground start asks for Face ID.
- Before iOS 26 a transfer stops when the user leaves the app and resumes
  when they come back.

## Residual risks

- **No manual VoiceOver pass on a device:** the audits check labels,
  contrast, and sizes, not the experience of navigating with VoiceOver.
  Fix: a VoiceOver walk-through on an iPhone.
- **Background limits:** transfers run in the background only on iOS 26
  and later, in the continued-processing task the user's send or accept
  asked for; sends queued by the share extension or a shortcut wait for
  the app, and nothing resumes on its own. Fix: none on iOS within §10.3;
  the Live Activity and notifications say what waits.
- **Face ID is decided when the profile is created:** setting a passcode
  later does not gate an existing profile (its key's access control is
  fixed when stored). Fix: a re-key that stores the storage key again
  under a presence-gated Secure Enclave key, offered in Settings.
- **Discovery can be crowded out:** a LAN host advertising many
  well-shaped instances holds the 64 resolve slots (each until it goes or,
  unresolved, for 30 seconds), so contacts may be found late. The same
  holds for any mDNS browser. Fix: rank slots by what the discovery table
  could match (the label alone does not say), or evict the oldest.
- **mDNSResponder restarts** lose up to 5 seconds of advertising and the
  instances seen (found again as they are re-announced). Fix: none needed.
- **The scanned QR secret is a Swift `String`** (O5). Fix: a scanner path
  that hands the core bytes it can wipe.
- **App Group data:** contact names and keyed IDs (and the key that makes
  them), the visibility setting, and queued files (until sent) are
  readable by todoke's own extensions; the names, IDs, and key are in the
  App Group's defaults, which iCloud and Finder backups include (the
  queued files are excluded). Fix: keep the names out of the group (the
  extensions would show IDs only) or accept, as now: none of it opens the
  profile or a session.
- **The minimum (iOS 17) was tested on an iOS 26.5 simulator only:** no
  iOS 17 runtime is installed here. Fix: run the tests on iOS 17 and 18
  runtimes in CI.
- **The share extension copies files** (twice the space until sent).
  Fix: none without running the core in the extension.
